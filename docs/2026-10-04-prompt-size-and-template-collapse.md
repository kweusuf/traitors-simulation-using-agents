# Prompt size and template collapse

Two things happened in October 2026 that turned out to be one thing: the
room started speaking in templates, and every prompt had grown past forty
thousand characters. This note records what was measured, what was tried,
and what is still unproven.

## The symptom

Public messages repeating an earlier one, verbatim, sometimes emitted by
many different players. In one diagnostic run a single sentence appeared
ten times from eight senders.

Counting this correctly mattered more than it sounds. An early write-up
reported 38% of messages repeating, by pooling public and private messages
into one number. Split by channel, public repeats at 23% and private at
11%. Pooling inflated the figure by about 1.6x, and a private DM repeating
text is not the room speaking in one voice. Every rate below is public-only,
computed by `tools/repeat_rate.py` and `tools/compare_arms.py`.

## What the prompts actually contained

`prompt_chars` in a run folder says a prompt was 55,000 characters. It does
not say what those characters were spent on, which is the difference between
"the transcript is too big" and "the transcript is a reasonable size and
something else is eating the budget".

`tools/prompt_composition.py` renders the same view with sections excluded
and differences the results, so each number is real builder output. For one
agent in round 3 of a 22-player season:

| Section | Chars | Share |
| --- | --- | --- |
| system prompt (fixed) | 1,180 | 2% |
| state header | 656 | 1% |
| legal targets | 130 | 0% |
| public transcript | 33,744 | 49% |
| private threads | 30,543 | 44% |
| instructions + memory | 2,782 | 4% |
| **total** | **69,035** | |

Two things follow. The fixed parts are not worth optimising - under 3%
between them. And 93% is transcript, at 846 characters (about 211 tokens)
per message.

The private side is worth a note: `transcript_messages_per_prompt` applies
*per thread*, so an agent in several conversations gets that budget once per
thread rather than once in total. That is why private reached 44% for one
reader and why it scales with the number of conversations a player is in.

## Why size is the prime suspect

A model that has run out of usable context does not report an error. It
degrades into the highest-probability completion. Given a transcript where
every line begins "Tom, you've been...", the highest-probability completion
is another line beginning "Tom, you've been...".

That predicts something specific, and the prediction held: agents with
*different* prompts emitting *identical* text. Measured on the diagnostic
run, the eight players behind one repeated line had eight different prompt
lengths (3,425 / 4,418 / 4,425 / 4,431 / 4,437 / 4,440 / 5,053 / 5,059), and
only 2 of 77 prompt lengths were shared across senders. They were not being
fed the same prompt. They were each equally unable to see the room.

It also predicted the latency profile, which is prompt-processing cost:
p50 around 90 seconds per call, climbing with prompt size.

The context window was never the limit. The server reported 131k tokens
against prompts of about 8k early and roughly 17k by round 3. What grows is
the transcript, unbounded, until the model stops tracking it.


## Two strategies, four arms

**Co-generated pointers.** Ask the model, in the call that writes the
message, for a one-line pointer to what it just said. It costs no extra
generation, and it is the only moment the model is reasoning about the
message. The pointer then feeds the existing decay curve in
`ShortTermMemory.recalled`, which already scores `salience * decay ** age`
against a floor, scaled per observer.

**Pointer memory.** Store a decaying pointer for *every* message, not only
for the ones the show's rules make worth keeping. This is the half that lets
the transcript shrink: without a short trace to fall back on, there is
nothing for a smaller window to decay into.

Asking for a pointer and requiring one are different requests, so they are
separate flags:

| Config | `co_generate_gist` | `gist_required` | `pointer_memory` |
| --- | --- | --- | --- |
| `season_uk_s01.fix_en.yaml` (base) | - | - | - |
| `season_uk_s01.ptr_opt.yaml` | on | - | - |
| `season_uk_s01.ptr_req.yaml` | on | on | - |
| `season_uk_s01.ptr_mem.yaml` | on | on | on |

Generated by `tools/make_pointer_arms.py` from the base config rather than
written out, so four near-identical YAML files cannot drift apart in a way
nobody intended. `tools/verify_pointer_arms.py` loads each one and checks
its diff against the base is nothing but the flags.

## Three ways this could look like it worked

**A missing pointer is not a failure.** `usable_pointer` falls back to the
deterministic first-clause gist, so the worst case is the previous behaviour
rather than a run stalling on retries. That safety is also the trap: an arm
in which the model never produces a pointer scores exactly like one in which
it works well. The co-generation rate is recorded in the event log and is
meant to be read every time. `tools/schema_check.py` prints it.

**A copied pointer is not a distillation.** A model answering "summarise
this" by echoing the opening clause has added a line without distilling
anything, and the memory would read no better while costing more.
`usable_pointer` compares normalized text, so reflowing whitespace or
changing case cannot smuggle a copy through, and a pointer longer than 160
characters is capped.

**The mandatory arm could have been the optional arm.**
`Action.__get_pydantic_json_schema__` rewrites the schema's `required` list

## Results

Public repeat rate, verbatim, public channel only:

| Run | Arm | Msgs | Repeat | Rate | Max shared | p50 prompt | Failed |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `uk-s01-en3` | base (older) | 574 | 141 | 25% | 9 | 51,995 | 13% |
| `uk-s01-en4` | base | 225 | 52 | 23% | 8 | 40,626 | 15% |
| `uk-s01-en5` | base | 259 | 85 | 33% | 13 | 38,058 | 17% |
| `uk-s01-ptr-mem` | pointers + memory | 509 | 82 | 16% | 5 | 26,486 | 14% |
| `uk-s01-ptr-req` | pointers only | (in progress) | | | | | |

The pointer arms produce a real pointer on 100% of messages, none of them a
copy of the message head, at a median of 0.19x the message's length. The
most-shared pointer in `ptr_mem` appeared four times, which matters because a
pointer every player shares would be a new way to cause the exact collapse
being fixed.

`uk-s01-en5` is a partial run, killed at round 4 once its repeat rate had
climbed from 23% to 33% while its prompt grew to 55,591 characters. It is
kept because a run that degrades is evidence about prompt growth, not just a
number to discard.

## What is not established

**One run per arm, and they are different lengths.** `ptr_mem` finished at
509 messages over 11 rounds; `ptr_req` was 281 messages at 5 rounds when
last measured, and its rate had drifted from 14% to 19% as it went. A gap
that narrows with sample size is a gap that may not be a gap. A second seed
per arm is the minimum before any of this is a benchmark rather than an
anecdote.

**Pointer memory's contribution is unproven.** `ptr_req` differs from the
base only in asking for a pointer, and sits at 19% against the base's 23-33%.
`ptr_mem`, which adds memory on top, finished at 16%. The simpler change is
at least as good so far, but the arms have not been run to comparable
lengths and the memory half is neither confirmed nor excluded.

**An earlier explanation was wrong.** The prompt curve flattening in
`ptr_mem` was first attributed to pointers giving the transcript something to
decay into. That is not what happened: both pointer arms sit at about 26k
because `transcript_messages_per_prompt: 40` caps the window. The pointer
memory did not reduce the transcript window. Correcting this matters because
it points at a different next lever - the window itself, and what happens
when it is tightened without pointer memory to absorb the loss.

**Repetition is reduced, not solved.** 16-19% is still too high for natural
speech. Whatever the pointers bought, the remaining collapse has another
cause that this did not identify.

**Latency did not improve.** An early claim that the pointer arm ran four
times faster with no failures was drawn from 51 calls in round 1. Over the
full 1,007 calls, `ptr_mem` ran at p50 81s with 14% failures, against the
base's 94s and 17%. Shorter prompts did not make the host faster. The
early-round sample was noise.

**Illegal targets persist.** The most recent error in `ptr_req` was
`target 'kieran' is not legal; choose one of: ['aisha']` in a two-player
finale. That is unrelated to pointers - it is the `target` field - but it is
the same class of failure the phantom gate addresses, and worth watching.

## What to try next, in order

1. **Second seed for each pointer arm.** The current evidence cannot separate
   two single runs of different lengths, and that is the specific question
   left open.
2. **Tighten `transcript_messages_per_prompt`.** It is the real cap on
   prompt size, and both pointer arms show it working. Nothing has been run
   with it below 40.
3. **Sampling controls** (temperature, `repeat_penalty`,
   `presence_penalty` via `llm.options`) before changing model. Cheap,
   reversible, and it keeps every existing run comparable.
4. **The model itself, last.** It is the most expensive lever and it
   invalidates the most: the UK and Hinglish pairs stop being comparable and
   every run so far becomes a different experiment.
